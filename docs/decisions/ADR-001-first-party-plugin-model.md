# ADR-001：第一方插件模型（Task 001）

- 状态：已接受（2026-09-06）
- 关联：`docs/tasks/001-first-party-plugin-kernel.md` · `docs/architecture/design.md` §插件内核 · `docs/architecture/api.md` §Plugin 接口

## 背景

清羽的三大能力（快速启动、剪贴板、截图）目前全部由 `AppContainer` 硬编码组装：搜索源、窗口控制器、后台服务直接互相引用，贡献（搜索源/菜单/快捷键/设置页）没有统一的所有权边界。下一阶段（docs/tasks 001–009）要在不破坏现有行为的前提下，把三个内置功能迁移到统一的功能模块模型上，并为 004（五页设置）与 009（截图接线）提供聚合点。

## 决策

1. **插件 = 编译期第一方模块**。插件只由项目所有者开发，以源码形式随主应用编译、签名和发布；`PluginRegistry` 不扫描磁盘、不加载外部 Bundle、不提供 SDK 或插件市场。插件运行在主应用进程内，跟随主应用安装、升级与卸载。
2. **注册表是唯一聚合点**。插件通过 `QingyuPlugin.manifest` 声明贡献：搜索源（`SearchSource`）、动作（`PluginAction`）、设置页、菜单项、全局快捷键与所需权限（`PermissionKind`）。`PluginRegistry` 按注册顺序聚合，设置页/菜单按 `order` 排序，供搜索、设置、状态栏等消费方查询。
3. **动作按稳定 ID 路由**。跨模块调用使用 `PluginActionID`（Codable、稳定），不使用通知字符串作为插件 API。动作只能由所属插件注册的闭包执行；所属插件停用、启动失败或未知时执行抛错。
4. **生命周期**。注册表在 `@MainActor`。`startAll()` 逐个启动已启用插件，单个 `start()` 抛错仅记录并隔离该插件（状态 `failed`，贡献隐藏），不阻断其他插件；`setEnabled(_:for:)` 持久化启停选择（UserDefaults 键 `plugin.<plugin-id>.enabled`）并同步启动/停止；停用调用 `stop()` 并使贡献不可见。
5. **可见性规则**。贡献可见 ⇔ 已注册 && 已启用 && 非 `failed` && 非 `stopped`。注册后未调用 `startAll()` 前贡献即可见（注册即声明）；启动失败是唯一在启动阶段收回贡献的路径。
6. **权限按需声明**。插件只在 manifest 声明 `requiredPermissions`；本任务不实现运行期权限请求 UI，由后续设置/集成任务消费。
7. **当前阶段行为不变**。Task 001 只交付内核并在 `AppContainer` 创建空注册表；既有硬编码接线全部保留，功能迁移发生在 Task 002/003，截图接线在 Task 009。

## 后果

- 好处：三个内置功能获得统一的所有权、启停与贡献模型；设置页/快捷键/菜单聚合有单一事实来源；为多插件协作（动作 ID 路由）提供基础。
- 代价：增加一层间接性；`AppContainer` 在迁移完成前同时存在注册表与硬编码两条路径（临时双轨，009 收敛）。
- 隔离边界：插件同进程运行，共享主应用全部权限与数据，**没有进程级隔离**。该模型成立的前提是"只有项目所有者能新增插件"。若未来需要运行时加载第三方插件，必须重新评审：权限模型、代码签名与校验、崩溃与故障隔离、数据访问边界，并重写本 ADR 与 Task 001 的实现。
