# 设计评审：验证手段与已知盲区

这份文档记录清羽（Qingyu）界面评审所用的验证手段，以及**当前环境无法验证**的部分。
目的是让后续维护者知道：哪些结论有真实渲染证据支撑，哪些只是代码层面成立。

## 一、可用的验证手段

### 1. 离屏渲染快照（`QingyuTests/DesignSnapshotTests.swift`）

用 `ImageRenderer` 把真实 SwiftUI 视图渲染成 PNG，断言渲染成功、像素尺寸一致、画面非单色。
覆盖：剪贴板空/加载/行列表/最小宽度、设置 section（常规与大字号）、组件对照、详情空态。

**局限**：AppKit 支撑的控件（TextField / Toggle / ProgressView / List）会被画成黄色占位块。
看到黄色方块不代表界面坏了，只代表「此处不可离屏验证」。

### 2. 真实窗口自绘（`--uitest-capture-png <path>`）

让窗口用 `cacheDisplay(in:to:)` 把自己画成 PNG。走视图自己的绘制路径，
AppKit 控件、滚动内容、侧栏列表都能真实绘制。

配套参数：
- `--uitest-capture-delay <秒>`：截图前等待时长
- `--uitest-capture-window-size`（见 `--uitest-window-size <WxH>`）：改窗口尺寸
- `--uitest-dark-appearance`：强制深色外观（系统级偏好无法伪造，只能进程内设）
- `--uitest-large-text`：把 `JadeFont.scale` 设为 1.35
- `--uitest-search-query <文本>` / `--uitest-search-slow <秒>`：命令栏结果与搜索中状态
- `--uitest-toast <文本>`：在剪贴板窗口里显示一条 toast
- `--uitest-open-pin`：打开贴图窗口
- `--uitest-clipboard-disabled`：强制剪贴板关闭态
- `--uitest-recording-paused`：把剪贴板切到「暂停记录」态
- `--uitest-force-row-hover`：强制结果行悬停态（检查「隐藏此结果」按钮）
- `--uitest-trigger openClipboardSettings` / `openScreenshotSettings`：直达对应设置页
  （**注意**：`openSettings` 只打开通用页；不要用它代表「设置页已验证」）

**局限**：`cacheDisplay` 会跳过 `PlatformContainer` 里的滚动内容（窗口 PNG 里那块显示为空白）；
钩子会额外把每个滚动文档单独导出为 `<base>-scrollN.png` 绕过。


### 3. 状态注入通道（只能靠这些才能覆盖「非常规状态」）

常规截图只能拍到默认状态。以下 DEBUG 钩子专门用来构造难以触发的状态，
**每个都对应过至少一个真实缺陷**：

| 参数 | 用途 | 发现的真实问题 |
| --- | --- | --- |
| `--uitest-recording-paused` | 剪贴板暂停态 | 暂停横幅曾与工具栏重复提供「恢复」按钮 |
| `--uitest-force-row-hover` | 结果行悬停态 | 悬停按钮与行内其它图标撞档 |
| `--uitest-isolated-plugins` | 插件启停写内存，不污染真实偏好 | 原先 UI 测试会改用户插件设置 |
| `--uitest-disable-plugin <id>` | 启动前停用指定插件 | 停用后侧栏/命令栏/菜单三处不同步（3 轮修复） |
| `--uitest-dump-menu` | 把菜单项**校验结果**写进日志 | NSMenu 无法截图；据此验证菜单随插件启停 |
| `--uitest-force-empty-reason <reason>` | 强制命令栏空状态原因 | 三种空状态曾共用一条误导文案，CTA 还指向错页 |

**注意**：`--uitest-dump-menu` 必须读 `validateMenuItem` 的结果，而不是 `item.isEnabled`——
NSMenu 只在菜单真正展开时才应用 `autoenablesItems`，新建项恒为 `true`。

**注意**：验证空状态要同时构造「空」和「原因」。只设原因、查询却有结果时，空状态根本不渲染。

### 4. 插件 ID 是带连字符的

`PluginID` 的真实值：`"quick-launch"` / `"clipboard"` / `"screenshot"`。
`setEnabled` 对未知 ID 会返回并在日志留一条 error——传错 ID 时表现为「毫无变化」，
容易误判成 UI 没刷新。

## 二、当前环境无法验证的部分

| 项目 | 原因 |
| --- | --- |
| 截图会话与贴图工具条 | 需要真实屏幕录制授权（`screencapture` 报 `could not create image from display`） |
| 悬停提示 / hover 底色 / 焦点描边 / 穿透虚线 | 需要真实鼠标与键盘焦点，离屏渲染无法呈现 |
| VoiceOver 实际朗读 | 需要真实辅助功能会话 |
| 系统「增强对比度」渲染 | 系统级偏好，`NSWorkspace` 读数在进程内无法伪造 |

这些项目的相关代码已按规范实现并有单元测试兜底，但**没有视觉证据**。
修改这些区域时，请在有屏幕录制授权与真实指针/辅助功能的环境中重新验证。

## 三、自动化门禁

`./scripts/verify.sh` 依次执行：
1. `git diff --check`（空白错误 / 冲突标记）
2. `Localizable.xcstrings` JSON 合法性
3. **本地化一致性**（`scripts/check-localization.py`）：五语言齐全、en/fr 不得含中文、禁止中英并排
4. 测试文件登记检查
5. 全量单元测试（含设计快照、颜色对比度、字号缩放、相对时间等回归）

已知的一类**不覆盖**：代码层硬编码的用户可见字符串（例如存储层写入的 `summary`）。
资源文件里的文案由第 3 步覆盖，代码里的字面量需要人工审查。

### 3. 已人工核对过的真实渲染（截至第 247 轮）

下列页面/状态已用真实窗口自绘验证过：

- 剪贴板窗口：空态、加载态、有内容、选中详情、最小尺寸、宽屏、深色、
  中文/日文/法文、大字号、剪贴板关闭、暂停记录、不可用内容（原因条 + 禁用主按钮）、
  toast、长文本、图像条目
- 命令栏：空态、有结果、搜索中、无匹配、**无源（插件停用）**、
  **源被关掉**、深色、大字号、法文
- 设置五页：通用、快速启动、剪贴板、截图、关于
  - 通用：插件管理、搜索黑名单、权限、数据区，浅色/深色/法文/大字号/最小尺寸
  - 剪贴板设置页：快捷键（含恢复默认）、记录开关、保留期、隐私说明、清空全部记录
  - 截图设置页：13 个分组，浅色 + 深色
  - 关于：反馈表单与链接区，法文 + 大字号
  - **订正**：FeatureGate.screenshotEnabled 当前为 true，截图设置页可见；
    此前文档写「截图设置被 FeatureGate 隐藏」是错的
- 标注编辑器：常规宽度（工具条带文字）、最小宽度 680（工具条切图标模式）、深色
- 首启引导：浅色、深色、大字号（卡片三行等高，无「恢复默认」噪音）
- 贴图窗口：静态外观（图片 + 缩放/透明度/旋转叠加）；悬停工具条需真实指针，见第二节

**插件状态相关**（靠状态注入通道验证）：停用插件后侧栏隐藏对应页、
插件行显示「已停止/开关关闭」、命令栏不再返回其来源结果、菜单「截图」项置灰。

**关于副标题的双语对照（不是缺陷）**：命令栏结果里设置项/系统命令的副标题显示英文名，
是 PRD §02-ui-spec 明确要求的「固定显示对应中英文名称」——帮助用户确认该项的命令名。
看到英文副标题不要当作未翻译。

### 4. 命令栏 / Toast 截图的时间窗（踩过坑）

命令栏是浮窗，两个状态的截图对时序敏感，默认 `--uitest-capture-delay 5` 往往截不到：

- **命令栏空态**：延迟 >= 4s 稳，浮窗需先就绪
- **命令栏有结果**：延迟约 3s（查询在 show 后 0.4s 注入）
- **命令栏搜索中**：需配合 `--uitest-search-slow 3.0`，采样窗口约 2–3s
- **命令栏无结果**：延迟约 4s（搜索完成后）
- **Toast**：show 后 0.6s 触发、仅存活 1.6→2.2s，延迟必须落在约 1.0–2.0s；
  用默认 5s 只会截到空窗口（这是排查过多次才定位的）

**可靠做法**：先用后台 `open` 启动，再轮询目标文件是否出现（`for i in $(seq 1 15); do sleep 1; ls <png> && break; done`），
而不是固定 sleep 一个值——浮窗就绪时间不稳定，固定 sleep 会随机截空。

## 四、靠读代码发现不了、必须看真实排版的缺陷类型

第 205 轮在引导页发现一个一直存在的排版缺陷：一段 ad-hoc 说明被放进了
放两个按钮的 HStack，说明被挤在右侧窄列里折成四行、左侧大片留白。
代码「能编译、逻辑正确、测试全绿」，但视觉上是错的。

同类需靠渲染才能发现的缺陷：

- **元素混行**：说明文字 / 多行文本被塞进本应只放按钮或短标签的 HStack
  → 检查方法：HStack 里是否同时有 Button 和带 `fixedSize(horizontal:false)` 的 Text
- **窄列折行**：同一行里并排放了长度悬殊的内容，短的那侧被压成多行
- **对齐漂移**：右对齐的按钮列因文案长短不一导致左边缘参差
- **大字号溢出**：1.35× 下固定尺寸容器装不下内容

这些用一次真实截图 + 像素量测就能定位；只看代码或只看测试报告会漏掉。

### 本会话（第 217–247 轮）新增的三类

- **语义色「角色」混用**：同一个颜色既当填充又当前景，两种门槛不同（填充看前景对比，
  前景看 4.5:1）。`systemRed` 作文字只有 3.46:1、作按钮填充白字 3.55:1；
  `systemGreen/Orange` 作图标也只有 2.1:1。
  处理方式：把语义色拆成 `xxx`（填充/图标）与 `xxxText`（文字前景）两组令牌。
- **符号与语境撞形**：`app` 这个 SF Symbol 字形就是一个空圆角方块，
  放在启用开关旁边会被读成占位符或复选框。代码完全合法、测试也不会报。
  处理方式：换成语义更明确的符号（`square.grid.2x2`）。
- **缩略图观感不可靠**：深色截图里一个按钮看着像「浅蓝底白字」（1.9:1），
  实际采样是 `#51688B` 深板岩、白字 5.67:1。**必须先采样像素再下结论**，
  否则会把正确设计改坏。

### 新 UI 会照亮旧假设

给通用页加「插件管理」之后，连续 5 轮发现的是**别处**的不一致：
插件「已启用却显示未启动」、停用后命令栏仍返回结果、恢复链路断掉、
菜单项不判权、设置侧栏不刷新。

共同特征：这些旧代码从未被质疑过，因为对应的能力此前对用户不可见。
**每新增一处「暴露内部状态」的 UI，都要回头检查那个状态在全链路上是否自洽。**
